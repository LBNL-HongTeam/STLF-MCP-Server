# explore-load-data

Find, profile and visualise a load dataset before any modelling. This skill is deliberately lighter than `train-forecast-model`: it never trains, tunes or merges, so its gates are advisory. The moment the user wants a model, hand off (§6).

The MCP tools own the logic; this skill sequences them and tells you what to look at.

---

## Section 0 — MCP connection is mandatory

Every step uses the STLF-MCP-Server MCP tools. If a tool call fails because the server is unreachable, stop, report the raw error, and wait for the user. Never parse CSVs yourself, never draw charts yourself, never estimate a statistic a tool would have returned.

---

## Section 1 — Locate the data

1. **User gave a path** → use it. It may be absolute, or relative to the server's data roots (`data/examples/AMI/x.csv` and `AMI/x.csv` both resolve). If a tool answers "not found", the error lists the roots it searched — do not guess further; run `list_datasets` and show the candidates.
2. **User gave no path** (or asks what is available) → call `list_datasets` with no arguments. Present a short table: `relative_path`, `rows`, `frequency`, `start`→`end`, `n_columns`, and whether `datetime_column` was found. Then ask which file to explore. Never answer "no data is available" without having called it.
3. **Wide files** (many numeric columns such as one per feeder or substation) are one series per column. Ask which column is the target, or note that `batch_train_forecast_models` handles all of them later.
4. Parquet files are listed but the tools read CSV only; say so if the user picks one.

---

## Section 2 — Timezone (advisory here, mandatory before training)

Ask once, early: "What timezone are the timestamps in, and are they naive local strings or tz-aware?" Do **not** block inspection or plotting on the answer — exploring is safe — but:

- record the answer for the hand-off in §6;
- if `inspect_data` returns a `POSSIBLE_UTC` flag (non-midnight start) or `DST_MERGE_RISK`, surface it verbatim and repeat the question;
- never infer the timezone from the filename, an offset suffix, or the building's location.

---

## Section 3 — `inspect_data` (numeric profile)

Call `inspect_data(csv_path)` (add `column_mapping` only if the user has told you the roles). Report, in this order:

1. **Roles** from `columns`: `datetime`, `target`, `past_covariates`; then the hints —
   - `unrecognised`: numeric columns auto-detection did not map. If any looks like a driver (weather, occupancy, production), say it would need `column_mapping.past_covariates` to be used.
   - `future_covariate_candidates` (holidays, schedules, prior forecasts): known ahead of time; only usable via `column_mapping.future_covariates`.
   - `target_excluded`: columns skipped as the target because they look like forecasts or generation — confirm the chosen target is really the load.
   - `categorical_code_columns` (e.g. `weather_code`): not usable as linear inputs.
   - `redundant_calendar_columns` (e.g. `is_weekend`): already generated by the loader; ignore.
2. **Shape**: `frequency.inferred` (must be `15min`, `30min` or `h`), `time_range.start`/`end`, `n_rows_raw`, `coverage_pct`, `n_duplicates_removed`.
3. **Quality**: `gaps.n_gaps` / largest gap, `outlier_analysis` counts, every `quality_flags` entry verbatim.
4. **Verdict**: `ready_to_train` and `blocking_issues`. A blocking issue ends the exploration with a clear statement of what must change in the file; do not work around it.

Keep the numbers; the picture comes next.

---

## Section 4 — `generate_data_report` (visual profile)

Call `generate_data_report(csv_path)` — `output_html_path` is optional (the server writes under `outputs/reports/` and returns the path). Give the user the absolute `output_html_path` and say it opens directly in a browser (`file://`, no server needed).

Parameters worth setting from the conversation:

| Situation | Argument |
|---|---|
| User asked how the seasonal split looks, or the file spans ≥ 12 months | `split_strategy="seasonal"` (default) |
| User will train a non-Torch model, or the file is short | `split_strategy="sequential"` |
| User only wants to see the data | `split_strategy="none"` |
| A different hold-out fraction is planned | `validation_split=…` (0.05–0.5) |
| Many numeric columns, user cares about a few | `covariates=[…]` |
| Roles were confirmed in §3 | the same `column_mapping` |

What the page contains, so you can point the user to the right panel: summary + readiness badge; **time series** with training/validation drawn as blue/orange segments, season bands, gaps and ±3σ outliers, plus window buttons (full range, each season, each season's peak week); **split timeline** and segment table; **one panel per covariate** sharing the window, with `unmapped` tags; hour-of-day profiles by season and weekday/weekend; day-of-week and monthly bars; **day × hour heatmap**; **target-vs-covariate** scatter with a binned mean (a V against temperature is the heating/cooling signature); data-quality tables and the `inspect_data` suggestions.

Use the tool's own return value for the narrative: `split.summary` (rows per role and season), `unmapped_covariates`, `n_gaps`, `n_value_outliers`, `n_step_changes`, `peak_windows` (when each season peaks and at what value), `quality_flags`, `ready_to_train`.

## Section 5 — Interpretation checklist (say these things, when true)

- **Outliers are not automatically bad data.** Clusters of ±3σ points on consecutive afternoons in a heat wave, or a multi-day block in a cold snap, are real events (check the heatmap and the season's peak-week window). Isolated single-step spikes or zeros are more likely sensor or export faults. Say which you see; do not recommend removing anything without the user's judgement.
- **Unmapped columns are silently ignored by training.** If the report tags a plausible driver as `unmapped`, give the exact `column_mapping` that would include it.
- **Seasonal split quirk.** Winter is Dec + Jan + Feb, so in a calendar-year file January–February is entirely training and winter's validation block is late December. State this whenever `split.strategy == "seasonal"`; it is how `train_forecast_model` splits for LSTM/TFT/TiDE/TSMixer.
- **Short data.** Fewer than four seasons → the seasonal split falls back to sequential (`split.note` says so); fewer than ~90 days → say deep models are unlikely to be worth it.
- **Coverage < 95 %** or large gaps → the loader interpolates ≤ 2 h; longer gaps stay NaN and can break LinearRegression. Name the gap dates.
- **Frequency mismatch** between files the user intends to merge → must be resolved before `merge_covariates`.
- **Weather in a separate file** → point to the merge protocol in the `train-forecast-model` skill (`references/multi-csv-merge-protocol.md`); do not merge by hand.

## Section 6 — Hand-off

When the user wants to train, tune, merge, evaluate or backtest:

1. Load the training skill: `get_skill(name="train-forecast-model")` over MCP, or open `skills/train-forecast-model/SKILL.md` in a checkout.
2. Carry over, explicitly: the chosen `csv_path` (absolute), the timezone answer from §2, the confirmed `column_mapping` (including any `future_covariates`), `frequency.inferred`, and the `output_html_path` of the data report.
3. Its §1.0 timezone gate is a hard stop — if the user never answered in §2, that skill will ask again before any tool call.
